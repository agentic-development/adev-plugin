# Architecture

> Generated by $adev:document on 2026-03-31T00:00:00Z

## Project Overview

`adev_data_eval` is a dbt + DuckDB analytics project for a small e-commerce domain. The raw layer is represented as dbt seeds rather than `source()` definitions, and downstream models use `ref()` to move data through a three-layer warehouse pattern:

- `staging` models standardize seeded raw data
- `intermediate` models apply reusable business logic
- `marts` models publish business-facing fact and dimension tables

## Layer Map

| Layer | dbt resource type | Schema | Materialization | Models |
|------|--------------------|--------|-----------------|--------|
| Raw | `seed` | `raw` | seed tables | `raw_customers`, `raw_orders`, `raw_products`, `raw_payments` |
| Staging | `model` | `staging` | `view` | `stg_customers`, `stg_orders`, `stg_products`, `stg_payments` |
| Intermediate | `model` | `intermediate` | `table` | `int_orders_pivoted_to_payments`, `int_customer_order_history` |
| Marts | `model` | `marts` | `table` | `fct_orders`, `dim_customers`, `dim_products` |
| Historical tracking | `snapshot` | `snapshots` | snapshot table | `snapshot_orders` |

## Model Layers

### Seeds

The raw layer is loaded from CSV files in `seeds/` and materialized into the `raw` schema by dbt seed:

- `raw_customers`: customer master data
- `raw_orders`: order headers with status and total in cents
- `raw_products`: product catalog with prices in cents
- `raw_payments`: order payments by payment method

### Staging Models

Staging models are 1:1 with seeds and are materialized as views. They do light cleanup only: renaming, type casting, and simple standardization.

| Model | Upstream | Key behavior |
|------|----------|--------------|
| `stg_customers` | `ref('raw_customers')` | Renames `id` to `customer_id`, casts `created_at` to `date` |
| `stg_orders` | `ref('raw_orders')` | Renames order fields, casts `order_date`, converts `total_amount_cents` to `order_total` |
| `stg_products` | `ref('raw_products')` | Renames product fields, converts `price_cents` to `price`, casts `created_at` |
| `stg_payments` | `ref('raw_payments')` | Renames payment fields, converts `amount_cents` to `amount`, casts `payment_date` |

### Intermediate Models

Intermediate models are materialized as tables and centralize business logic that should not be duplicated across marts.

| Model | Inputs | Purpose |
|------|--------|---------|
| `int_orders_pivoted_to_payments` | `ref('stg_payments')` | Pivots payment rows into one row per order with separate payment-method amount columns |
| `int_customer_order_history` | `ref('stg_orders')` | Aggregates customer order history into first/most recent order dates, order count, and lifetime value |

### Mart Models

Mart models are materialized as tables for downstream analytics consumption.

| Model | Inputs | Grain | Purpose |
|------|--------|-------|---------|
| `fct_orders` | `ref('stg_orders')`, `ref('int_orders_pivoted_to_payments')` | one row per order | Core fact table with status, date, customer, and payment breakdown |
| `dim_customers` | `ref('stg_customers')`, `ref('int_customer_order_history')` | one row per customer | Customer dimension enriched with lifetime metrics |
| `dim_products` | `ref('stg_products')` | one row per product | Product dimension with cleaned catalog attributes |

## Key Transformations

### `cents_to_dollars`

The reusable macro `cents_to_dollars(column_name)` rounds a cent-valued integer column to a 2-decimal currency amount:

```sql
{% macro cents_to_dollars(column_name) %}
    round({{ column_name }} / 100.0, 2)
{% endmacro %}
```

It is used in:

- `stg_orders` to derive `order_total`
- `stg_products` to derive `price`
- `stg_payments` to derive `amount`

### Payment Pivoting

`int_orders_pivoted_to_payments` converts the long payment stream into a wide, order-grain structure:

- `credit_card_amount`
- `bank_transfer_amount`
- `gift_card_amount`
- `total_amount`

This makes `fct_orders` easy to consume without repeating payment aggregation logic.

### Customer Order Aggregation

`int_customer_order_history` computes reusable customer metrics from `stg_orders`:

- `first_order_date`: `min(order_date)`
- `most_recent_order_date`: `max(order_date)`
- `number_of_orders`: `count(order_id)`
- `lifetime_value`: sum of `order_total` for orders where `order_status = 'completed'`

`dim_customers` then left joins these metrics onto all staged customers and uses `coalesce(order_history.lifetime_value, 0)` so customers with no completed orders still have a usable metric.

## Testing And Quality Strategy

### dbt Schema Tests

The project defines 48 YAML-based dbt tests across staging, intermediate, and mart models:

- `staging`: 27 tests using `unique`, `not_null`, `relationships`, and `accepted_values`
- `intermediate`: 4 tests validating primary keys on reusable tables
- `marts`: 17 tests covering fact/dimension keys, foreign keys, and constrained attributes

Representative examples:

- `stg_orders.customer_id` has `relationships` to `ref('stg_customers')`
- `stg_payments.payment_method` is constrained with `accepted_values`
- `fct_orders.customer_id` has `relationships` to `ref('dim_customers')`

### Singular Data Tests

There are 3 custom SQL tests in `tests/`:

- `assert_customers_with_no_orders_have_zero_metrics.sql`
- `assert_orders_have_valid_status.sql`
- `assert_positive_order_amounts.sql`

These complement schema tests by expressing business rules directly in SQL against refs.

### Snapshot Strategy

`snapshot_orders` is an SCD Type 2-style dbt snapshot over `ref('stg_orders')` with:

- `unique_key = 'order_id'`
- `strategy = 'check'`
- `check_cols = ['order_status']`

This preserves order history whenever status changes.

### Orchestration And External Quality Checks

Airflow and Great Expectations extend dbt’s native quality controls:

- `dags/dbt_daily_run.py` orchestrates `dbt seed`, source-oriented test selection, staged runs by layer, `dbt test`, and `dbt snapshot`
- `dags/data_quality_check.py` runs Great Expectations checkpoints after model builds
- `great_expectations/expectations/raw_customers_suite.json` validates raw customer identifiers, nullability, country domain, and row count bounds
- `great_expectations/expectations/raw_orders_suite.json` validates raw order identifiers, nullability, status domain, amount bounds, and row count bounds

## Onboarding Notes

- Start with `dbt_project.yml` to understand schemas and materializations by layer
- Read staging models first; they define the canonical renamed columns used everywhere else
- Treat intermediate models as the reusable business logic layer for marts
- Use `ref()` lineage in the marts to understand how customer and payment logic is composed
- If you need historical order status behavior, inspect `snapshot_orders` rather than only the current marts
