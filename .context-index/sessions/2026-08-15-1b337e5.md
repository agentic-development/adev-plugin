## Intent

docs(governance): split the extension-merge strand into its own spec

The BLOCK->revise loop halted on REGRESSED at revision 4 — two consecutive
revisions closed blockers while introducing new ones, and three warnings
survived three revisions untouched. That is the signature of two contracts
trapped in one spec, which is the same failure that dissolved
measurement-integrity.spec.md.

The split is by contract, not convenience. extension-governance-merge-hardening
claims "an extension's contribution writes exactly what it declared, only where
it is permitted, and never mutates what it did not create" — a security property
over untrusted input, provable against the registries exactly as they stand
today. explicit-governance-registries claims "what a governance file contains is
what runs" — a composition property. They share files but not a failure mode.

The split immediately resolves one of the four open blockers: the YAML scalar
escaping defect (security-reviewer:input-validation:02aeddff) is entirely an
extension-merge concern and moves with it. The other three stay with the
composition spec, where they belong.

Dependency is one-way and explicit. The registries spec populates transitions:
in gates.yaml, which the current merge deletes, and its drift pass keys on
source, which the hardening spec stamps. The one rule that could have gone
circular — refusing extension install into a registry lacking materialized_at —
is owned by the registries spec, since the marker is its construct; the
hardening spec anticipates it by reserving "any marker owned by the composition
model" as installer-immutable.

Extension-merge scope removed from the registries spec: 6 behaviors, 5 error
cases, 8 acceptance criteria and the Step 3 body all moved. Step 3 is now a
dependency gate. Behaviors renumbered 1-12.
