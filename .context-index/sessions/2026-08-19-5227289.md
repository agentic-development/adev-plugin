## Intent

fix(domains): resolveDomain reads top-level manifest.domain, not nested project.domain

resolveDomain()'s project-level check read manifest.project.domain, but the
production writer (writeDomainKey() in lib/cli/domain-extension-picker.mjs)
writes a bare top-level `domain: <name>` key, matching this repo's own
manifest.yaml and templates/manifest-template.yaml. Any project that
installed a non-default domain extension had its domain silently ignored by
every resolveDomain() consumer (governance/materialize.mjs, cli/domain.mjs,
gates/gate.mjs, lifecycle-gate-helpers.mjs, hygiene/registry-drift.mjs,
gates/gate-sets.mjs), falling back to the "software" default undetected
because DEFAULT_DOMAIN happens to also be "software".

Also removes the now-redundant `{ project: { domain } }` wrapping in
lib/lifecycle-gate-helpers.mjs, which existed only to paper over this same
mismatch by hand-nesting a top-level regex match.

Empirically verified: a scratch project with top-level `domain: web-service`
plus the web-service extension installed now correctly resolves 6 reviewer
entries (source: domain:web-service) via
`adev governance materialize --registry review`, instead of silently
falling back to the software domain's 7-entry default panel.
