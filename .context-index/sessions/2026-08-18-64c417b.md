## Intent

docs(charter): pull xg1f.6 into reviewer-domain-fit Phase A

Template resolution cannot see CLI-installed extensions: resolveTemplate scans
<pluginRoot>/extensions/*/domain/ and its signature carries no project root,
while `adev extension install` writes to <projectRoot>/.context-index/domains/.
An installed domain supplies reviewers.yaml and gates.yaml — loadDomainConfig
reads the project-local path first — while its spec-template.md and
charter-template.md are never found. Install reports success and delivers part
of what was declared. Invisible so far only because both first-party extensions
are vendored plugin-side, where resolveTemplate does look.

Pulled into scope because the initiative already ships domain-owned content on
both sides of this split: Phase A gives domains their reviewer prompts and Phase
2 gives them specify-guidance.md, both resolving project-local via
loadDomainConfig. Leaving templates plugin-only would ship a domain-package
contract that is two-thirds true, and would mean web-service is only deliverable
vendored — making user-installable domains nominal rather than real.

Phase A now widens resolveTemplate with a project root and searches
.context-index/domains/<domain>/ ahead of the plugin-side extension roots,
mirroring loadDomainConfig's precedence. Three acceptance criteria added: an
install-not-vendor test asserting /adev:specify writes from an installed
extension's template, project-then-plugin precedence, and preservation of the
existing fall-through so template-resolution.spec.md Behaviors 3 and 4 still hold.

lifecycle-artifacts dependency reason updated — it now genuinely modifies
resolveTemplate rather than only the templates it returns.

Side effect worth noting: this removes one of the six blockers recorded on
xg1f.5 (unbundle software), whose Out of Scope entry is updated to say so.
