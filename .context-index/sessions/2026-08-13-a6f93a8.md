## Intent

fix(hooks): merge-guard blocked read-only plumbing and every PR merge

Three defects, all found by the guard firing on commands it was never meant to
catch — repeatedly, across a session of ordinary PR work.

1. `git\s+merge\b` also matched `git merge-base`, `git merge-tree`, and
   `git merge-file`. `-` is a word boundary, so three read-only plumbing
   commands that write nothing were refused whenever the current branch was
   protected. Blocking a query is pure friction, and a guard that cries wolf
   is one operators learn to route around — which costs more than the guard
   ever saved. Now requires a space or end-of-string.

2. The PR-merge clause sat INSIDE the loop over protected branches and ignored
   the loop variable entirely. Consequences, both observed rather than
   theorised: a PR targeting a NON-protected base (a stacked PR onto another
   feature branch) was refused, and the refusal named whichever protected
   branch came first — a branch the PR never targeted. The advice it printed,
   "create a feature branch and open a pull request instead", is also
   unactionable when the command being refused IS a pull-request merge.

3. The guard matches the raw command STRING, so it fires on prose that merely
   mentions these commands — a commit message describing this very fix was
   refused. Not fixed here (parsing shell to find real invocations is a larger
   change than this PR should carry) but recorded in the spec, with the
   workaround: pass long messages via `git commit -F <file>`.

The DEFAULT for agent PR merges deliberately does not change: still blocked.
An existing test asserted that block, so it was intent, not accident — merging
is where review is enforced and an agent should not land work unattended.
What changes is that it is now a named policy rather than a side effect of
loop placement: `completion.allow_agent_pr_merge: true` opts in, only the
exact literal `true` counts, and the refusal message names both the real
target and the knob.

Verified against the live repo manifest: `git merge-base` now exits 0, and the
PR-merge path still exits 2 here (this project has not opted in).
