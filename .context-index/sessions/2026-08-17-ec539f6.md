## Intent

test(review): assert 22p-bis denylist parity for manifest entries

No new denylist code. BEH-11's 'a denied path is never named' is not
entailed for control-character paths — deferred to adev-plugin-j7pq.7
(SEC-2), asserted as current behavior.

Test-only: no production change was needed. The denylist filter runs in
Pass 1, before the manifest branch groups anything, so the three codes
are already delivery-agnostic. Assertion 2 ('the denied path is never
NAMED') was green on the first run — the manifest body and files[] both
source from the post-denylist safe set — and was verified rather than
assumed.

All three denylist codes are reachable and each is asserted positively.
CONTEXT_PACK_DENYLIST_MATCH is reached by an enumerated include carrying
a TRAILING SLASH: expandGlob normalizes separators so the walk still
finds the file, while isDenied is anchored on the raw glob string and
cannot match through the trailing '/'. An earlier draft of this suite
claimed the code was unreachable on the strength of the symlink case
alone; that claim was false and is removed. The symlink behaviour (a
symlink is silently unmatched because expandGlob filters on lstat-based
Dirent.isFile()) is retained as its own distinct assertion.

A second gap is pinned as an executable marker: on the DENYLIST_MATCH
path the denied file's glob is still named in the emitted no-matches
header, and rendered is non-empty while errors is non-empty. That is
inherited rev-4 behaviour — inline delivery emits the same glob as
path="…" — so BEH-11's 'retained verbatim' requirement and its ban on
new codes put the fix in adev-plugin-j7pq.7, not here.
