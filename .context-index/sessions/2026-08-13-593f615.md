## Intent

fix(issues): point the beads --db at the database file, not the .beads directory

`br init` creates a `.beads/` DIRECTORY holding the SQLite database
(`beads.db`) plus sidecars. BeadsAdapter set `dbPath = join(projectRoot,
".beads")` and passed that as `--db`, but br 0.2.22 requires `--db` to
name a regular FILE and rejects a directory with:

  CONFIG_ERROR: Refusing unsafe configured database leaf
  <database-authority sha256=...>: expected a regular file, not a
  symlink or special file

thrown before the subcommand runs. The whole beads backend was therefore
non-functional -- not just `adev issues migrate`, but every
create/update/close/list.

The surface symptom misdirects: `adev issues migrate --to beads` reports
MIGRATE_PARTIAL_FAILURE naming the first issue it tried, which here had
backticks and the word SECURITY in its title, reading exactly like a
shell-quoting or injection bug. It is not -- the adapter uses
execFileSync with array args and never invokes a shell. A plain title
fails identically. Verified both directions before changing anything.

`--db` is kept, not dropped in favour of br's own workspace discovery:
getIssueManager constructs the adapter with resolveStorageRoot()
(registry.mjs:62,97), which deliberately resolves to the MAIN repo even
when the caller runs inside a linked git worktree. Letting br walk up
from cwd would find the wrong `.beads`, or none. The flag was right; the
path it named was wrong.

resolveBeadsDbPath() prefers `.beads/beads.db`, falls back to a single
`*.db` if a store is named differently, ignores non-.db sidecars
(beads.db-shm, beads.db-fsqlite-ns-gate), and returns the canonical path
when `.beads/` does not exist so a pre-init call surfaces br's own
"not initialized" error rather than a path-shaped one.

One pre-existing test asserted the old directory path. It is UPDATED,
not weakened: the requirement changed, because that assertion described
a path that could never work against br 0.2.22. The reasoning is
recorded inline at the assertion.
