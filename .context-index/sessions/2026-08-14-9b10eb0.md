## Intent

docs(governance): revise to rev 4 — define materialized_at, fix Behavior 4's substrate

Both rev-3 blockers were prior warnings whose consequence rev 3 itself
elevated, and both are now closed.

materialized_at became the sole discriminator of a fail-closed guard in rev 3,
but nothing said what writes it, and the only candidate writer contradicted
itself: Behavior 6 promised materialize "makes no other change" and is
byte-identical on re-run, which read literally means the marker is never
stamped and every registry raises REGISTRY_NOT_MATERIALIZED forever with a
remedy that cannot work. Rev 4 declares it in ADDED with shape, location and
owner — a top-level root key, ISO-8601, write-once — and splits Behavior 6
into the stamp and preserve cases so idempotency stays true. /adev:init
scaffolding stamps it too, so fresh projects are not born un-materialized.

Behavior 4 read per-gate outcomes from the lifecycle event log, which has no
such record: CANONICAL_EVENTS has no gate variant and Check 1 emits one
aggregate validator_report, so gate ids are never event subjects. Every
transition check would have FAILed every required gate — build-breaking once
Step 4 promotes rules to error. Rev 4 extends Check 1's existing payload with
a per-gate outcome array instead of adding an event variant, which keeps the
change inside this spec's authority rather than crossing ADR-0009's
[BOUNDARY: human-approved] line, and adds a staleness rule so an outcome
predating the current source-manifest SHA records SKIP rather than a pass.

Also corrects the highest-value warning: Step 3 still described the protected
-key-list approach that Behavior 16 repudiates. An implementer following the
migration section rather than the contract would have rebuilt the command
injection path. Step 3 now says delete the fill-gap loop, and says why a key
list cannot be made safe — command is a legitimate gates.yaml field.
