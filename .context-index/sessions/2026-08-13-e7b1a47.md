## Intent

refactor(issues): make beads the single source of truth — delete the sidecar

The beads backend kept two board states: `.beads-map.json` (adev ids plus
every field br had no column for) and, for epics, `tasks.json`. That is a
design smell with a demonstrated cost — the fail-open fixed in 3da84a65
existed precisely because requireClaimable read the sidecar while exclusivity
lived in br's `assignee`. Patching each divergence is endless; deleting the
second store ends the class.

br 0.2.x has a native home for all of it:

  adev id (issue-N / epic-N)  → external_ref (br enforces uniqueness)
  owner / claim holder        → assignee, and nowhere else
  epics                       → br issues with issue_type: epic
  parent/child                → --parent (native dep edge)
  everything else adev tracks → agent_context JSON, under an "adev" key

Two behaviours found by experiment, each of which would have caused silent
data loss:

- `br list` HIDES closed issues by default. Every internal scan passes
  `-s all`; without it, minting recycles a closed issue's id and get()
  returns null for closed items the json backend returns.
- `--agent-context` REPLACES the whole field. Every metadata write is
  read-modify-write, or a claim silently erases `branch`. Foreign top-level
  keys are preserved — agent_context is br's field, not adev's.

Claim and lease stamp are now ONE call (`update --claim --agent-context …`),
and br rolls the context write back when it refuses the claim, so holder and
stamp cannot disagree. Previously two writes with a crash window between.

Still not atomic, stated plainly rather than glossed: stale-lease TAKEOVER.
`--claim` refuses any held issue and `--assignee` has no compare-and-set, so
expiring a lease needs two calls. Id minting is likewise not atomic — but it
fails LOUDLY, because br rejects a duplicate external_ref, so the outcome is a
failed create, never two issues sharing an id.

Migration is automatic, not detect-and-refuse: a user who never runs an
unadvertised command would otherwise just see an empty board. It covers BOTH
legacy stores — dropping the epic delegation without it would have vanished
tasks.json epics, which unlike the sidecar were the only copy. Every step is
keyed on external_ref, so re-runs are no-ops and a half-finished run resumes;
files are renamed `.migrated-<ts>`, never deleted; an unmigratable sidecar
throws BEADS_LEGACY_MIGRATION_FAILED and stays on disk.

Two other sidecar consumers would have broken silently and were fixed:
lib/cli/issues-migrate.mjs (already_migrated now derives from the target
board) and the session-capture hook path, which reads br with checkBr:false
and autoMigrate:false so a hook can never write.

Verified independently of the change author: a real board creates no
`.context-index/tasks` directory at all; `br list` alone shows the epic, the
issue, its external_ref and its adev context; and the human-claimed-via-br
gate case still exits 2. Full gate 5558 pass / 0 fail; live beads bucket 18/18.
