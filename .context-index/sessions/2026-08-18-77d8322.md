## Intent

docs(charter): address charter-review findings on reviewer-domain-fit

Charter review returned Issues Found with all 8 factual claims confirmed but
one misattributed. Five issues, all addressed.

Misattribution (mine): the charter treated resolveTemplate and
templates/domains/software/spec-template.md as one mechanism. They are two.
skills/specify/SKILL.md:159 loads templates/domains/<domain>/spec-template.md
for interview structure; Step 5 (:455) WRITES from resolveTemplate(), which
resolves extensions/<domain>/domain/ -> templates/spec-template.<kind>.md and
never touches templates/domains/. Current State now documents both trees, and
specify-guidance.md is pinned to the domain-config set (DOMAIN_CONFIG_FILENAMES,
loaded via loadDomainConfig) rather than left ambiguous between them.

Gap that split created: the AC "/adev:specify contains no HTTP status codes" did
not cover templates/spec-template.behavioral.md:79 or spec-template.refactor.md:145,
both carrying an "HTTP Status / Error Code" column — and those are the templates
actually written into every new spec. Web-shaped guidance would have survived
Phase 2. New AC covers them.

Dependencies: added domain-profiles (Phase D modifies three of its stated
invariants) and lifecycle-artifacts (owns resolveTemplate, named by a Phase D
criterion).

Phase D vs Out of Scope contradiction, resolved by operator decision to keep
software bundled. domain-config.mjs:203 requires extends to name a BUNDLED
domain, and both first-party extensions declare `extends: software` — removing
it from BUNDLED_DOMAIN_NAMES would throw EXTENDS_DEPTH_EXCEEDED for both. The
set carries two meanings today: a resolution branch (loaded from
templates/domains/) and a presence guarantee (safe extends target). Phase D now
keeps the guarantee and drops only the branch, so extends resolves unchanged,
the one-level rule is untouched, and zsmh.5 stays legitimately out of scope
because the only extended domain is guaranteed installed.

Phase D acceptance criteria rewritten accordingly, plus an upgrade-path
criterion the review found missing entirely: a project already carrying
`domain: software` in manifest.yaml must keep resolving after upgrade, asserted
from a pre-upgrade fixture rather than a fresh init.

Phase D AC 3 was unfalsifiable — "still resolves templates, with an explicit
diagnostic rather than a silent fallback" is satisfied by both throw-with-
diagnostic and warn-then-resolve. Now fail-closed explicitly, matching the
posture of materialized governance registries.
