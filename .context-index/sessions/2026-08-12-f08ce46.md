## Intent

fix(gate): remove two mappings that made gates pass unconditionally

`SKILL_STEP_MAP` mapped `brainstorm -> "brainstorm"` and `retro -> "retro"`.
Neither name is a member of `STEP_ORDER`.

`priorStepOf` computes `idx = STEP_ORDER.indexOf(step)` and returns null
when `idx <= 0`. That condition is true for `specify` (idx 0, which
legitimately has no predecessor) AND for any step not in the list at all
(idx -1). Both entries therefore resolved to "no prior step required",
so `adev gate require --skill brainstorm` exited 0 on a project with no
lifecycle history whatsoever — two gates that looked enforced and
enforced nothing.

Neither skill sits in the gate chain and neither has a call site in
skills/ or providers/, so both entries are simply removed. Those
invocations now report an unknown skill instead of succeeding.

Adds `isGatedStep(stepName)` to lib/lifecycle-state.mjs and calls it in
the CLI before `requireGate`, so a future map entry naming a
non-STEP_ORDER step fails closed with UNKNOWN_GATE_STEP rather than
silently passing. `priorStepOf` keeps its current behaviour — callers
that legitimately pass non-lifecycle steps still work — but the
conflation is now documented at both sites.

Deliberately unchanged: `specify` (idx 0) still passes on a fresh
project, and `route` stays in OPTIONAL_GATE_STEPS so `implement` does
not require it.

Tests: tests/cli/gate-no-op-mappings.test.mjs. The invariant is that a
gate for any step other than the first must BLOCK on a project with no
lifecycle history — a mapping that silently passes is indistinguishable
from one doing its job, which is how this went unnoticed. The supported
skill list is read from `help()` output so new mappings are covered
automatically. Verified to fail 3/5 against the pre-fix mapping and pass
5/5 after; full suite green at 5126 tests.
