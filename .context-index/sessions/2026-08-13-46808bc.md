## Intent

fix(issues): give the beads adapter real epic support instead of a read-only delegate

createEpic/updateEpic/listEpics all delegated to FileAdapter, whose write
methods unconditionally `throw deprecatedWrite()` because the markdown
backend is read-only. Epics were therefore impossible to create on the
beads backend BY CONSTRUCTION -- not a config problem. This aborted
`adev issues migrate --to beads --include-closed` after all 308 issues
had migrated but before a single epic did: 0 of 106 epics and 0 of 41
dependency edges landed.

The representation is taken from the task-management charter, not
invented: the Domain Model defines "WorkItem | Generic tiered work unit
(unifies former Epic and Issue entities)" and Constraints state legacy
flat ids "operate as root-level WorkItems". An epic is therefore stored
exactly as an issue is -- a real br item tagged `--type epic` (verified
br 0.2.22 accepts it and echoes issue_type: "epic") -- with the fields
beads does not model (milestone, planRef, status) in .beads-map.json
under an `epic-N` key. That is the same split backend-adapters.spec.md
already prescribes for epicId/planRef, "since beads does not track these
fields natively".

Fixing createEpic alone would have been incoherent: listEpics delegated
to the same read-only adapter, so epics would have been written and then
unreadable. All three methods move together, which is the minimum
coherent unit.

Epic ids count only epic-N keys, so issue creation cannot consume an
epic id -- covered by a dedicated regression test.

8 new tests, mock-only (_runBr stubbed, no br required), matching the
sibling beads adapter test idiom. npm test: 5704 tests, 5702 pass,
0 fail, 2 pre-existing todo.
