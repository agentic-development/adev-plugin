## Intent

docs(research): add the coordination-gate finding to the harness study

Found by executing the study's own Phase 0 rather than by the four
investigations — the artifact corpus records what each run did, never
what two runs did at once.

While Phase 0 was being filed and worked, a second workstream was active
on the same shared board (epic-102, issues 568-581, PRs #210-#214),
pursuing substantially the same goal. Neither side saw the other: two
agents fixed the same p0 command injection an hour apart (PR #214 and
duplicate #215, both citing issue-582), and this study re-derived
several conclusions epic-102 had already itemised.

Root cause is an asymmetry between two state stores. The issue board
resolves storage via `git rev-parse --git-common-dir` and is shared
across worktrees; execution state reads a worktree-local path and is
not. Measured live: /adev:work Step 1 reported status "idle" while four
issues were in_progress and five PRs were open. The behavioural half is
that nothing re-reads an issue when work begins, so stale local
knowledge beat the shared record — the board was already marking
issue-582 in_progress.

The structural point: the framework has code-enforced gates for
lifecycle ORDER and none for concurrent OWNERSHIP. Every gate in the
Part 3 inventory answers "is this step allowed yet?"; none answers "is
someone already doing this?"

Remedy filed as epic-107 (issues 606-610), all reusing existing
machinery: extend the Step 1 scan, resolve execution state through the
board's existing resolveStorageRoot(), an `adev issues claim` modelled
on the requireGate precondition pattern, issue-to-branch/PR binding, and
claim TTLs. The claim verb is blocked by issue-594 (JsonAdapter
concurrent-appender failure) — which surfaced only because the Phase 0
test-discovery fix restored the suites that had never run.

Adds Phase 0a to the roadmap: coordinate before simplifying.
