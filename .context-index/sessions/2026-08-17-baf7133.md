## Intent

test(review): assert 22p-bis denylist parity for manifest entries

Test-only: every assertion passed on the first run, so no production
change was manufactured. The Pass-1 denylist filter runs before the
manifest branch groups anything, and Task 4 already sourced both the
manifest body and files[] from the POST-denylist safe set, so the
distinguishing claim -- 'the denied path is never NAMED' -- held
already. It is now pinned so a later refactor cannot quietly re-source
the body from the pre-filter match set.

Also asserts rev-4 inline behavior is retained verbatim for the same
three fixtures (same codes, same severities) rather than assumed, and
freezes the module's declared code vocabulary at source level so adding
a code trips the suite even when no fixture reaches it.

No new denylist code. BEH-11's 'a denied path is never named' is not
entailed for control-character paths -- deferred to adev-plugin-j7pq.7
(SEC-2), asserted as current behavior.

Second finding, also pinned as current behavior: the enumerated case
raises CONTEXT_PACK_DENYLIST, not CONTEXT_PACK_DENYLIST_MATCH, because
for a wildcard-free include the literal-glob check sees the same string
the resolved-path check would. The symlink-evasion route that would
reach DENYLIST_MATCH is unreachable -- expandGlob filters on
lstat-based Dirent.isFile(), so a symlink is never matched at all. The
outcome is safe (the denied target is never named) but the code has no
live caller.
