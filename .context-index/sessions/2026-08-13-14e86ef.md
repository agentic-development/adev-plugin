## Intent

fix(execution-state): resolve storage root across worktrees like the board

Closes issue-607. The issue board has been worktree-shared since
resolve-root.mjs started resolving through `git rev-parse --git-common-dir`.
Execution state was not: it read <projectRoot>/.context-index/, which is
worktree-local. Measured live — /adev:work Step 1 reported status "idle" in
this worktree while four issues were in_progress and five PRs were open.

Reuses resolveStorageRoot() rather than adding a second resolver, mirroring
the same migration lib/milestones.mjs already made. tasks.db_path is honored
as the existing unified knob (templates/manifest-template.yaml already
documents it as governing tasks.json and milestones.json); a separate
execution_state.path would let the board and the state referencing its issue
IDs drift to different roots.

validateProjectRoot still runs FIRST and unchanged, so no existing
INVALID_PROJECT_ROOT throw can be bypassed by resolution. The realpath
containment check, the basename check, the temp-path check, and the atomic
temp-then-rename are all re-anchored at the storage root rather than relaxed.

Canonicalizing the storage root was found by a failing test, not inspection:
a manifest db_path of /var/folders/... vs its realpath /private/var/folders/...
made containment throw on first write. git rev-parse returns canonical paths,
so only the manifest route exposed it.

Design Constraint 3 in the spec is amended rather than left standing: its
claim that the three state-artifact modules cannot diverge on path safety was
made false here, since lib/lifecycle-state.mjs stays worktree-local. It now
reads as parity on validation for all three, parity on resolution only for
the modules holding live shared state.
