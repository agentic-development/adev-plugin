## Intent

fix(hooks): merge-guard blocks git merge only when current branch is protected

The merge-guard hook blocked any 'git merge' command that mentioned a
protected branch anywhere in its arguments — including 'git merge
origin/main' run FROM a feature branch. That's the routine "keep my PR
current with main" workflow; operators were forced into 'git rebase
origin/main' as a workaround.

Root cause: the regex 'git\s+merge\s+.*\b${branch}\b' uses a word
boundary, so 'main' matched inside 'origin/main'. The detection clause
didn't consult the current branch at all.

Fix: block 'git merge' iff the CURRENT branch is protected. What matters
is which branch the merge would advance, not which ref is being pulled
in. Existing 'git push <protected>', 'gh pr merge', and 'git checkout
<protected> && git merge' clauses are unchanged — those have different
threat semantics and stay unconditional.

Tests: added a Bug 3 regression case that asserts 'git merge origin/main'
from a feature branch is allowed; added a complementary case asserting
the same command FROM main still blocks. Rewrote one existing test
("blocks git merge to main") whose name conflated "targets main" with
"on main" — the corrected semantics is "on main".

Hook protocol unchanged (stdin JSON, exit codes 0/2). Charter inventory
entry stays accurate.
