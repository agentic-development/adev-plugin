### user

What is CRDT?

### assistant

**Conflict-free Replicated Data Type** — a data structure designed so that replicas edited independently can always be merged automatically, with a deterministic result, without coordination.

The defining property is that the merge operation is **commutative, associative, and idempotent**. Order of delivery doesn't matter; duplicate delivery doesn't matter. Any two replicas that have seen the same set of changes compute identical state — which is exactly the guarantee the grite paper quoted: *"two replicas that have seen the same events compute identical state regardless of delivery order."*

## Contrast with what git does

Git does a **three-way merge**: compare both sides against a common ancestor. When the two sides changed overlapping regions, git has no rule for who wins, so it stops and emits conflict markers for a human.

A CRDT never stops. The tie-break rule is *built into the data type*, so there's always an answer. That's the trade: you give up human judgment and get guaranteed automatic convergence.

## Two families

| Family | What replicates | Merge |
|---|---|---|
| **State-based** (CvRDT) | Whole state | A `merge(a, b)` function that's a least-upper-bound — order-independent by construction |
| **Operation-based** (CmRDT) | Individual operations | Ops are commutative; each replica replays them and lands in the same place |

git-bug and grite are operation-based: they store an append-only log of events and *rebuild* current state by folding over it.

## Common types

- **G-Counter** — grow-only counter; merge takes the max per actor, then sums.
- **G-Set** — grow-only set; merge is union. Worth noticing: `merge=union` in your `.gitattributes` on the lifecycle JSONL is effectively a poor-man's G-Set. Lines only get added, union is the merge, and that's *why* it's safe there.
- **LWW-Register** — single value, last-writer-wins. Needs a total order on writes; grite uses `(timestamp, actor, eventID)`, and git-bug deliberately avoids wall-clock, ordering by git DAG topology → Lamport clocks → hash.
- **OR-Set** — add/remove set with per-element unique tags, so a concurrent add and remove resolve predictably instead of depending on arrival order.

grite mixes these per field: scalars are LWW, sets (labels, assignees) are commutative.

## The caveat that matters for your board decision

**CRDT guarantees convergence, not preservation of intent.**

Everyone ends up with the same state. That state is not necessarily what either author wanted. LWW *discards* the loser's write — deterministically and silently, but it discards it.

This is precisely the point in the study: JSONL + last-writer-wins is technically conflict-free, and it's still the wrong choice for the board, because a silently dropped status update is what causes duplicate work. "No conflict markers" is not the same as "no data loss."

Where CRDTs genuinely beat both git-merge and LWW is on **set-valued** fields — two agents adding different labels both get their label, no conflict, nothing lost. That's the part of grite's design that outperforms file-per-issue. For scalar fields like `status`, a CRDT is just picking a winner by rule, which is what LWW does; file-per-issue instead surfaces it as a conflict a human resolves.

## Collaborative editing — the flagship

- **Yjs** is the dominant JS implementation — it powers TipTap, BlockNote, ProseMirror bindings, and JupyterLab's real-time collaboration.
- **Automerge** (Ink & Switch) is the other major one — a JSON-shaped CRDT, and the flagbearer for the "local-first software" movement.
- **Zed** built its multiplayer editing on a CRDT over a rope data structure.
- **Apple Notes** syncs via CRDTs under CloudKit.
- **Figma** is worth citing carefully: their multiplayer system is *CRDT-inspired* but server-authoritative, not a pure peer-to-peer CRDT — they picked per-property last-writer-wins with a server as the ordering authority.

**The notable loser: Google Docs uses Operational Transformation, not CRDTs.** OT was the incumbent approach for decades — it transforms concurrent operations against each other, but generally needs a central server to sequence them. CRDTs traded that away for the ability to merge without a coordinator. The OT-vs-CRDT argument is still live, and OT holds a lot of production ground.

## Databases and geo-replication

| System | Use |
|---|---|
| **Redis Enterprise** | Active-Active geo-replication ("CRDBs") is genuinely CRDT-based |
| **Riak** | Riak DT — the classic production implementation, counters/sets/maps/registers |
| **Cassandra** | Per-cell last-write-wins — effectively an LWW-register |
| **Azure Cosmos DB** | Multi-region writes with LWW conflict resolution |
| **AntidoteDB** | Research system, transactional CRDTs |

**SoundCloud's Roshi** is a well-known reference implementation — an LWW-element-set built over Redis for their activity timelines.

## Distributed systems infrastructure

- **Phoenix Presence** (Elixir) is my favorite concrete example: tracking who's online across a cluster is exactly a set with concurrent adds and removes, so it uses an ORSWOT CRDT. No central registry, nodes gossip, state converges.
- **Akka Distributed Data** offers CRDTs for cluster-shared state.

## Version control and dev tools — closest to your thread

- **Radicle** (peer-to-peer git) stores issues and patches as "collaborative objects" backed by CRDTs — the same problem you're looking at, solved this way.
- **git-bug** and **grite**, as covered.
- **Pijul** is adjacent rather than CRDT: a VCS built on commutative patches, reaching a similar "merge order doesn't matter" property from patch theory instead.

## Local-first apps

**Actual Budget** is a good open-source read — explicitly CRDT-based with hybrid logical clocks, and the author wrote it up in detail. **Liveblocks**, **Triplit**, and **Jazz** sell CRDT sync as a product. **ElectricSQL** — the company behind PGlite from earlier — is in this space too, which is precisely why PGlite assumes a sync layer above it.

## The honest caveat

CRDTs carry real costs, which is why they haven't swept the field:

- **Metadata overhead.** Deletions usually leave tombstones, so state grows monotonically unless you engineer garbage collection. Automerge and Yjs both spent years on this.
- **Interleaving.** Naive text CRDTs can interleave two people's concurrently-typed words into nonsense — correct by the convergence definition, garbage to a reader.
- **Complexity.** You're encoding merge policy into the type system rather than deferring to a human.

That last one is the tie-back to your board. CRDTs pay off where **merges are frequent, conflicts are semantically benign, and a human resolving them is impractical** — cursors, presence, labels, counters. Your board inverts two of those: merges are infrequent, and a conflicting `status` change is exactly the case where you *want* a human to look. Which is why file-per-issue came out ahead despite CRDTs being the more sophisticated machinery.
