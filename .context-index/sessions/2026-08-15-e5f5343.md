## Intent

docs(governance): hardening spec rev 4 — keep executable contributions, bound them three ways

Rev 3 excluded gates.yaml to close the command-injection sink. That was wrong
twice. validate.yaml carries an identical sink (kind: quality-gate + command)
and was left open, so the sink moved rather than closed. And the alternative
rev 3 offered — contribute a diagnostics runner instead — does not exist:
nothing under lib/extensions/ writes into .context-index/diagnostics/, so
extensions would have had no execution surface at all, while the one shipped
extension was refused with no valid rewrite.

Rev 4 takes the operator's direction: extensions may contribute executables,
made explicit and bounded. Three independent rules, applied uniformly to both
command-bearing registries rather than as a per-registry exception:

  Containment — every argv element naming a path must resolve inside the
  extension's own installed directory (resolvedPath, the first argument to
  installExtension), verified with the resolve + startsWith + realpath pattern
  installSamples already uses. argv[0] may be an allowlisted interpreter.

  argv-only — never a shell string, so contributed metacharacters are inert.
  merge-gates already requires this for gates; it becomes uniform.

  Consent — an install declaring executables refuses without explicit
  per-install consent, interactive prompt or --allow-exec, recorded as
  exec_consented_at. The prompt has a home already in
  lib/cli/domain-extension-picker.mjs.

None of the three suffices alone: containment without consent still runs code
the operator never saw; consent without containment grants blanket permission.

The reference extension satisfies all three unchanged — its command already
points inside its own directory — so the capability is preserved rather than
described. gates.yaml returns to the writable set; five registries again.

Allowlists rebuilt once more against consumer code: the gates row is exactly
what merge-gates projects (:42-46), since fields outside that set are silently
dropped; kind is constrained to the four values validate-config accepts;
dispatch and package are object-valued and isValidGovernanceValue is extended
to one level of nesting, which it rejects today. Behavior 7 now covers array
elements and nested values, not only top-level scalars — parseFlowSeq and
parseFlowMap reparse them identically.
