## What this record is

This is the first Tier B pass over all twelve core-lifecycle scenarios (`tests/evals/skill-regression/scenarios/{hygiene,validate,review-specs,debug,route,write-test,implement,specify,plan,brainstorm,build,work}.md`, scored by the matching `rubrics/*.yaml`). Unlike the change-imminent tier's first pass (`tier-b-2026-08-27-01.md`), which independently exercised four of eleven scenarios and generalized the rest from shared infrastructure, **this pass independently, live-executed all twelve** — a fresh disposable copy per scenario, the real skill actually dispatched against it, no simulation. Tasks 1–7 already verified each rubric's semantic content at authoring time (cited below, from their own commit messages); this pass is the runtime half — the eight operator criteria the sibling's Task 9 defines, plus the four tier-specific refinements Task 8's own context packet names (board containment as a live check rather than a vacuous one, `HEAD`-equality as the load-bearing write-escape signal, the widest before/after window in either tier for `build --full`, and `ADEV_NO_INFRA` passed per-invocation).

**Execution model.** Twelve scenarios were run as parallel/sequential forked subagents, each building its own `createTempGitRepo()` + `scripts/eval-scenario-setup.mjs` copy, invoking the real skill (via the Skill tool or the CLI verb it wraps) against that copy, and reporting back a structured summary — never a raw transcript. One batch (`specify`, `plan`, `brainstorm`) failed mid-run on an account-wide session rate limit and was cleanly retried from scratch after the limit reset; the retries are the results recorded below.

## Real defects found (not fixed — filed here for a human to create board issues; `br` was in a pre-existing sync-conflict state during this pass — see Known Environment Issue, below — so no live issue could be filed)

**Severity: high — blocks the pipeline's own documented default mode.**

1. **`specify` + `build` (same root cause, found independently by both).** Under `lifecycle.step_pairing: strict` (the fixture's own committed default), `/adev:specify`'s Step 0 lifecycle-start event requires the spec file to already exist on disk (`lib/cli/report.mjs`'s `existsSync` check) — but the spec isn't written until Step 5. The start event can never be recorded, so the Step 6 completion event is refused (`ORPHAN_STEP_EVENT`). Consequence for `build`: because the lifecycle log never carries `specify: completed`, `/adev:review-specs`'s own gate (`adev gate require --skill review-specs`) hard-blocks with exit 2, even though `build`'s own build-state tracking correctly recorded specify as done. **`/adev:build --full` cannot complete against any brand-new spec while step-pairing is strict — the fixture's own default, and the exact combination this scenario exists to exercise.**

**Severity: medium.**

2. **`implement`.** `lib/issues/json-adapter.mjs`'s `claim()`/`get()`/`release()` search only `board.issues`, never `board.epics`. `/adev:implement`'s documented "claim the epic before dispatching" step therefore always fails with `Issue not found` against a real epic id on the JSON backend; the skill's own exit-1 "warn and continue" handling silently no-ops the epic-locking guarantee for the default zero-dependency backend.
3. **`implement`.** `skills/implement/SKILL.md` Step 2h's numbered list orders "emit `plan_task` done" before "commit," but `rubrics/implement.yaml`'s `plan_task_done_matches_commit` requires the done event to be timestamped *after* the commit. Following the skill's own listed order produces a rubric `not_met`. One of the two needs correcting.
4. **`plan`.** `skills/plan/SKILL.md` documents using "the CLI verb" for the `.partial` → final atomic rename, but the only generic rename verb (`adev artifact commit --from/--to`) hard-refuses any source that doesn't start with YAML frontmatter — while plan's own Incremental Authoring protocol requires its `.partial` to start with an HTML-comment `plan@1` marker instead. The two requirements are mutually exclusive; the correct underlying function (`lib/partial-artifact.mjs::commitPartial`) exists and works but is never wrapped by any CLI verb, so a literal `/adev:plan` run following its own SKILL.md would fail at this step.
5. **`brainstorm`.** `skills/brainstorm/SKILL.md`'s Step 5b header skips Step 5b **entirely** whenever `--module <name>` is used, with no carve-out for a run against an *existing* charter — but `rubrics/brainstorm.yaml`'s `product_md_module_map_updated_idempotently` element claims Step 5b-4 "always runs in `--module` mode with an existing `product.md`," which the skill's own documented behavior contradicts. Confirmed empirically: `product.md` stayed untouched through a full `--module orders` revision run.

**Severity: low / fixture-and-rubric gaps (baseline-fidelity, not product defects).**

6. **`hygiene`.** The `pv03`/`kc03` (orphan-source-file) criterion cannot currently be observed through the real skill: dispatching `/adev:codehealth` refuses with `INVALID_MANIFEST` because the fixture's manifest has no `hygiene.source_roots` key, so Pass 13 never reaches orphan detection. Needs either a fixture-manifest addition (`hygiene.source_roots`) or a rubric adjustment.
7. **`hygiene`** (incidental, unrelated to the fixture). `lib/repomap/graph.mjs::getCommitHash()` takes no root/cwd argument and calls bare `execSync('git rev-parse --short HEAD')`, trusting ambient `process.cwd()` rather than the analyzed root — silently records the wrong commit if the invoking process's cwd differs from the target root. `skills/repomap/SKILL.md` is also stale relative to `lib/repomap/index.mjs`: it documents a "v1 regex-only" mode with no `--mode` flag and claims regex mode writes both JSON artifacts, but the real implementation has full tree-sitter/regex dual mode and regex mode does not write those artifacts.
8. **`route`.** The `human_only_rationale_actionable` quality dimension's `unknown_when` clause is worded for "every task routes auto-agent" and doesn't precisely cover the run's actual mix (one assisted-agent, two auto-agent, zero human-only) — a minor rubric-wording gap, not a scoring failure.

## Methodology notes

- **No nested subagent dispatch inside a fork.** Five scenarios (`review-specs`, `write-test`, `implement`, `brainstorm`, `build`) call for the skill to dispatch its own subagents (parallel reviewers, TDD-writer, etc.); forked subagents in this pass could not spawn subagents of their own, so each substituted direct execution of that work, documented individually in its own report rather than silently skipped. This affects process-fidelity dimensions scored `unknown` (e.g. `dispatch_isolation_respected`) but not the artifacts those dispatches would have produced.
- **Bash working-directory persistence.** One fork (`brainstorm`, first attempt) found that a `cd` into the scratch copy did not reliably survive to a later tool call, contradicting the Bash tool's own documented contract. It caught this via `pwd` before any write occurred, aborted, and restarted prefixing every command with an explicit `cd <copy> && ...`. Later scenarios in this pass (`work`, `build`) were briefed on this and used the explicit-cd discipline throughout. Filed as product feedback separately. The write-escape capture protocol is the designed safety net for exactly this failure class, and in every scenario it was actually exercised as designed.
- **Shared `/tmp` unreliable for capture files.** An early scenario (`hygiene`) found its own before/after capture files missing from bare `/tmp` afterward, likely due to concurrent forks in this same pass writing to the same shared temp namespace. Later scenarios were instructed to use a unique subdirectory under the session scratchpad instead, and reported no further loss.
- **One full batch retry.** The `specify`/`plan`/`brainstorm` batch failed entirely mid-run on an account-wide session rate limit (`resets 12:30am America/Sao_Paulo`); all three were relaunched from scratch (fresh copies, no reused state) after the limit reset, and the retries are what's recorded above.
