### Problems

1. **Measured scope mismatch.** All 23 security-shaped issues on this repo's own board match path containment, subprocess interpolation, input trust, privilege posture, artifact leakage, or destructive filesystem operations — and zero match any of `security-reviewer`'s six scopes (authentication, endpoint exposure, PII-in-responses, injection, uploads, rate limiting). Asked to review this repo, a reviewer fabricated an injection surface in `loadResumeParser(...)`, a function that has never existed here (charter Business Intent).
2. **Measured evidence the current panel misses real defects a referent-checking reviewer catches.** The Phase 1 falsification gate (`falsification-gate.spec.md`, finding at `.context-index/research/referent-integrity-falsification-2026-08.md`) ran a `referent-integrity` reviewer against `he2`, `r5sc`, and `zx5` at their pre-fix revisions: 3 of 3 scorable runs caught the known defect with a citation that resolves. The existing 3-reviewer panel did not catch these on the same specs when they originally shipped.
3. **The hand-computed `blocker_id` instruction cannot be satisfied by the model that carries it.** All three current REGISTRY prompts instruct: "computed via `lib/blocker-id.mjs::buildBlockerId`" and describe hashing `<section-anchor>:<truncated-finding-text>` with SHA-256, taking the first 8 hex characters — and so does the fourth bundled prompt, `quick-synthesized-reviewer-prompt.md` (used in place of the registry for `--tier quick`), which this spec does NOT touch (see the Current State Structure table and the Migration Path note under Step 1). Every reviewer profile (`reviewer-fast`, `reviewer-capable`, `reviewer-reasoning` — `templates/governance/profiles.yaml`) extends `read-only`, which sets `filesystem: { write: deny, execute: deny }` and grants only `filesystem-read`, `search`, and `agent` — no shell category. A model under that posture cannot run a hashing routine; any 8-hex string it emits is typed, not computed.
4. **This repo's own registry already carries a project-scoped `referent-integrity` entry that the retargeted default panel is about to duplicate.** `.context-index/governance/review.yaml` is a materialized, write-once file (`materialized_at: 2026-08-15T19:35:30.978Z`); its Phase 1 `referent-integrity` row was added by hand, not through `adev governance materialize`. Retargeting `templates/domains/software/reviewers.yaml` (this spec) does not retroactively touch this repo's own already-materialized file — that only happens through a future `adev governance adopt` (Phase C, out of this spec's scope). Left unreconciled, an eventual adopt would introduce a second `id: referent-integrity` row, and `collectReviewers` (`lib/governance/review-config.mjs:421-434`) resolves a repeated `id` with a `REVIEWER_OVERRIDE` warning where "the last entry wins" — not a load failure, but a silent behavior change nobody asked for.
5. **Blocker counts do not converge across review rounds.** Five review rounds on one spec produced 4 → 4 → 3 → 4 → 8 blockers, the final round doubling rather than narrowing (charter Current State, "Measured blocker inflation").

### Improvements

1. The panel's scope matches the artifact class this project (and any Node CLI/plugin project like it) actually is, per the Phase 1 evidence: referent-existence checking, wiring reachability, and a concrete threat model replace generic web-app OWASP scopes as the DEFAULT.
2. No prompt asks the model to do something its execution profile forbids (compute a cryptographic hash). Every active prompt instead emits `section_anchor` + `finding-type`, exactly like the already-proven `.context-index/prompts/referent-integrity.md`.
3. Security coverage does not decrease: `boundary-reviewer` dispatches `always` (not `triggered`) with its threat-model checklist embedded directly in the prompt body, so there is no data file that could be deferred or omitted and silently disable the reviewer.
4. `structural-architect` and `security-reviewer` are disabled with a stated reason, not deleted; every project whose materialized registry already names their prompt files keeps resolving them unchanged.
5. The OWASP-scoped review is not lost — it is relocated to where it is opt-in (`web-service` domain), for the class of project it actually fits. A `web-service` project gets the FULL retargeted panel plus `security-reviewer`, not `security-reviewer` alone, because `web-service`'s own `reviewers.yaml` restates all six entries (see Target State / Structure) rather than relying on the `extends: software` fallback, which never fires once the child supplies its own file.
6. This repo's own pending duplicate-`id` collision (Problem 4) is named as a concrete Migration Path step rather than left for a future maintainer to rediscover.

### Deviation from the charter's literal Phase 2 acceptance-criterion wording

The charter (revision 2) states Phase 2's first criterion as: *"`blocker_id` comes from `adev heuristics signature --origin review-specs --blocker-id`."* Verified against `lib/cli/heuristics.mjs`'s `--origin review-specs` branch: that mode is **inherited**, not **derivative** — it requires an already-well-formed `blocker_id` as input (`parseBlockerId` is called on the value passed to `--blocker-id`) and reuses that id's own hash component; it has no mode that mints a `blocker_id` from raw inputs. Reading the criterion literally is therefore unimplementable: nothing can "come from" a command whose only input is itself.

This spec instead follows the same resolution `.context-index/prompts/referent-integrity.md` already adopted in Phase 1: **omit `blocker_id` entirely** from every active default-panel prompt's blocker findings, emitting only `section_anchor` + `finding-type`. `adev heuristics signature --origin review-specs --blocker-id <id>` remains exactly as documented in `skills/review-specs/SKILL.md`'s Step "6b-ter" — available for any reviewer that DOES emit a well-formed `blocker_id` by some other means — but no reviewer this spec touches does. This is a deliberate reinterpretation of the charter criterion's intent (no hand-computed hash), not a literal implementation of its command reference; the charter itself should be amended in the same change that implements this spec, to avoid the two disagreeing on record.

### Accepted trade-off: the default panel's `.blockers.md` auto-retry sidecar goes empty

Because all five active default-panel prompts omit `blocker_id` (previous section), every one of their blocker findings is classified `LEGACY_REVIEWER_OUTPUT` by the existing aggregator (`skills/review-specs/SKILL.md`, "Aggregator `blocker_id` validation," rule 1) and excluded from `.blockers.md`. Concretely: `.blockers.md` is never populated by the default panel, `/adev:build --full`'s `/adev:specify --revise` auto-retry loop never dispatches for a default-panel finding (it falls through to the pre-loop sidecar+fail-loud path instead), and Step "6b-ter" heuristics retrieval is skipped unconditionally for these findings (`SKILL.md:373`). This is an accepted, explicit regression versus the pre-this-spec state — not a silent side effect — because the alternative (a model-typed pseudo-hash) is exactly the failure mode this spec removes. Restoring a non-computed identity path for the auto-retry loop (e.g. the aggregator itself calling `buildBlockerId` from `section_anchor` + `finding-type` + real finding text, since that function is real code, not model output) is a follow-up, tracked separately and out of this spec's scope — it would touch `skills/review-specs/SKILL.md`'s aggregator, which this spec deliberately does not modify (see Dependencies).

## Behavioral Contract

### Behaviors

<!-- retired-behavior-ids: (none) -->

- **BEH-1** — **When** `adev governance materialize --registry review` runs against a new project **then** the resulting registry contains five enabled reviewers (`referent-integrity`, `wiring-reviewer`, `consistency-analyzer`, `boundary-reviewer` at `dispatch: always`; `termination-reviewer` at `dispatch: { triggered: { keywords: […], min_score: 1 } }`), each with an explicit `profile` and `context_pack`, and two disabled entries (`structural-architect`, `security-reviewer`), each disabled entry carrying a non-empty `disabled_reason`.
- **BEH-2** — **When** any of the five active default-panel prompts emits a `blocker`-severity finding **then** that finding carries `section_anchor` and `finding-type` but no `blocker_id` field, and no prompt instructs the model to compute a cryptographic digest.
- **BEH-3** — **When** `consistency-analyzer` reviews a spec **then** its `## Input` section names exactly what the `consistency` context pack delivers (constitution, platform context, parent charter, sibling specs, cross-cutting specs, ADRs), and its scope additionally covers ADR Compliance and Module Boundaries.
- **BEH-4** — **When** `wiring-reviewer` reviews a spec **then** for every producer (function, file, config key, or event field) the spec introduces, it states the consumer, the trigger, and the test that exercises it, flagging as `blocker` anything introduced with no consumer ("no caller") or written but never read ("write-only state").
- **BEH-5** — **When** `boundary-reviewer` reviews any spec **then** it evaluates the spec against the enumerated threat-model checklist embedded in its own prompt body and dispatches regardless of which files the spec touches (`dispatch: always`), so security coverage never depends on a trigger match.
- **BEH-6** — **When** a spec's rendered content matches `termination-reviewer`'s trigger (any of its configured keywords — `loop`, `retry`, `poll`, `polling`, `iterate`, `iteration`, `recurring`, `convergence`, `auto-retry` — present anywhere in the spec text, per `shouldDispatch`'s whole-content keyword scoring) **then** `termination-reviewer` dispatches and flags as `blocker` any loop/retry/poll construct it finds lacking a stated iteration cap, a cap-trip verdict, and an unattended-mode default. A spec containing none of these keywords does not dispatch it. **Note:** because several of these keywords (`loop`, `retry`, `iteration`, `convergence`) are common words in adev's own spec corpus (this spec included), `min_score: 1` makes `termination-reviewer` dispatch on a large fraction of real specs in practice — this breadth is accepted rather than incidental, since a false-negative (a real unbounded loop the reviewer never sees) is worse than a frequent no-op dispatch that finds nothing.
- **BEH-7** — **When** a project's already-materialized `review.yaml` names `plugin:review-specs/structural-architect-prompt.md` or `plugin:review-specs/security-reviewer-prompt.md` **then** `loadReviewConfig` continues to resolve those files unchanged, and the reviewer dispatches exactly as it did before this spec.
- **BEH-8** — **When** a project's active domain is `web-service` **then** its domain overlay resolves to all six entries declared in `extensions/web-service/domain/reviewers.yaml` (the five active default-panel reviewers plus `security-reviewer`, whose `prompt:` points at the unchanged `plugin:review-specs/security-reviewer-prompt.md` — no duplicated content), because domain config resolution is first-file-wins per config type and does not merge across the `extends` chain; a project whose active domain is `software` (not `web-service`) gets no `security-reviewer` entry.

## System Constitution Reference

- **Principle 1 — Minimize external dependencies.** No new runtime dependency is added anywhere in this migration. The `web-service` domain references the existing `security-reviewer-prompt.md` file rather than duplicating its content.
- **Principle 2 — Skills are primarily markdown.** All five active default-panel prompts remain plain markdown files with no companion code required to function; the one code-adjacent change (the `consistency` pack's added glob) is a declarative YAML edit, not new logic.
- **Anti-pattern — no hand-computed identifiers in prompts.** Every active prompt drops the SHA-256 hashing instruction this migration targets; none is reintroduced anywhere in the new prompts.
