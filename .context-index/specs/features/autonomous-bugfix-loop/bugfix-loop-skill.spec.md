## Invocation Modes

- `/adev:bugfix-loop [--max-bugs N] [--max-turns N] [--github-sync]` — the user-facing entry point. Selects and attempts one eligible bug, then self-re-invokes with `--resume` (copying `/adev:build`'s proven continuation discipline: fresh context per turn, explicit re-invocation, no shortcut pressure) until the board is drained of eligible bugs or a budget is hit.
- **Re-invocation is automatic, not human-triggered.** A non-terminal turn's own last action is to programmatically invoke `/adev:bugfix-loop --resume --resume-run-id <run_id>` again — exactly as `/adev:build`'s orchestrator re-invokes itself between pipeline steps — with no human approval, confirmation, or manual slash-command re-entry required between turns. This is what makes the loop safe to leave unattended: the only thing that stops the chain of self-re-invocations is reaching a terminal turn (`COMPLETE`/`BUDGET_EXHAUSTED`/`BLOCKED`), which prints the `ADEV-BUGFIXLOOP:` token as its final line instead of issuing another self-invocation. A human is needed only to make the very first `/adev:bugfix-loop` call, or to issue a manual `--resume` after a crash (the `--resume-run-id`-optional recovery case below) — never to advance from one normal turn to the next.
- `--resume [--resume-run-id <id>]` (internal) — used only by the skill's own self-re-invocation, mirroring `/adev:build --resume`. Not intended for direct user invocation. `--resume-run-id` is passed explicitly by the self-re-invocation call (the skill always knows its own `run_id` from the turn that just completed); `--resume` without `--resume-run-id` falls back to the most-recently-modified `bugfix-loop-runs-*.json` file, for the rare case of a manual `--resume` after a crash where the exact `run_id` wasn't captured.
- Optional composition with Claude Code's `/goal` — documented usage (`docs/`), not a skill invocation mode: `/goal /adev:bugfix-loop has run to completion, reading for the ADEV-BUGFIXLOOP token`. This is Claude-Code-specific and never a dependency of the skill itself (see charter Quality Attributes: Portability).

## Arguments

| Argument | Required | Description |
|---|---|---|
| `--max-bugs <N>` | No | Caps the number of bugs attempted in one run (across all self-re-invoked turns). Default: unbounded — the loop drains until no eligible bug remains or `--max-turns` is hit. |
| `--max-turns <N>` | No | Caps the number of self-re-invocation turns. Default: 20 — a conservative bound preventing an unbounded run when neither flag is set. |
| `--github-sync` | No | Enables the tracker-provider-bridge's inbound pull before each bug selection and outbound writeback after each attempt (sibling `tracker-provider-bridge` spec, Milestone 2). Default: `false` — the loop operates on the local board only unless explicitly enabled. |

## Output Contract

- Writes/updates `.context-index/lifecycle-state/bugfix-loop-runs-<run_id>.json` (flat, matching the existing `.gitignore` glob `.context-index/lifecycle-state/*.json` — a one-level-deeper `bugfix-loop-runs/<run_id>.json` path was reviewed and found to fall outside that glob, silently becoming git-trackable; this flat form stays covered without a `.gitignore` edit), tracking `BugfixLoopRun` state (`run_id` generated via `crypto.randomUUID()`, never derived from external input; `started_at`, `max_bugs`, `max_turns`, `bugs_attempted[]`, **`turns_completed` (integer, default 0 — incremented by exactly 1 at the end of every turn, whether or not that turn attempted a bug; this is the field `--max-turns` is checked against, distinct from `bugs_attempted.length`, which only grows on turns that reached an actual `/adev:debug` attempt — see the "each turn" budget-check step below for why the two counters diverge on claim-failure-exhausted turns; this spec's own revision 6 introduced `turns_completed` onto the `BugfixLoopRun` entity to fix that revision's WR-1 — the charter's Domain Model row is the entity's source of truth and now declares this field as of charter revision 9, closing the round-6 RI-1 gap where this spec added the field without ever registering it there)**, **`status` (the 4-value terminal-state enum — see the "start-of-turn status guard" bullet below for its consumer)**, **`degraded_sync_note` (string or null, default null — the field the sibling `tracker-provider-bridge` spec's Error Propagation writes a one-time note into after 5 consecutive degraded GitHub-sync turns; this skill is that field's sole reader, per the concrete consumer behavior specified below alongside the `ADEV-BUGFIXLOOP:` completion token)**) per the charter's Domain Model. This file's format/ownership is registered in ADR-0015's Decision-section table as part of implementation, per that ADR's stated requirement — matching the pattern the sibling `per-issue-attempt-cap` and `tracker-provider-bridge` specs already follow for their own new `lifecycle-state/` artifacts.
- **Start-of-turn status guard (the `status` field's named consumer):** before the per-turn budget check below runs — the very first thing any turn does after loading its run-state file — the skill reads back its own prior `BugfixLoopRun.status` and asserts it is `running` (the only non-terminal value in the charter's enum). This closes `status`'s write-only gap the same way the round-6 budget check closed `bugs_attempted[]`/`turns_completed`'s: `status` starts `running` at run creation and is written again only on the terminal turn (per the completion-token-to-persisted-status mapping below), so every non-terminal turn should observe exactly `running` here. If the guard instead finds `complete`/`budget_exhausted`/`blocked`, the turn treats this as an attempt to advance an already-terminal run — a defensive case that arises from a manual `--resume`/`--resume-run-id` reissued against a run that already printed its completion token, or a stray duplicate self-re-invocation racing behind the terminal turn. On that path the skill does not call `adev issues next`, does not touch `bugs_attempted[]`/`turns_completed`, and does not re-print a completion token; it exits non-zero with an explanatory message naming the persisted `status` value and instructing the operator to start a fresh `/adev:bugfix-loop` invocation (no `--resume-run-id`) instead. This mirrors how `degraded_sync_note` got a sole-reader treatment in revision 4 — `status` gets the same one-consumer treatment here rather than remaining audit-only. If the guard finds `running` (the expected case on every normal turn), the turn proceeds immediately to the budget check below.
- **Per-turn budget check (the `bugs_attempted[]`/`turns_completed` consumer):** before doing anything else — before calling `adev issues next` — every turn re-reads its own `BugfixLoopRun` run-state file and evaluates both budgets: (1) if `--max-bugs` was set and `bugs_attempted.length >= max_bugs`, and (2) if `--max-turns` was set (or defaulted to 20) and `turns_completed >= max_turns`. If either is already true, the turn does not call `adev issues next` and does not attempt a bug — it goes straight to the terminal path: writes `BugfixLoopRun.status: budget_exhausted` (per the completion-token-to-persisted-status mapping below) and emits `ADEV-BUGFIXLOOP: BUDGET_EXHAUSTED` as the final line, distinguishing in the run-state/notes which of the two caps tripped (`max_bugs` reached vs. `max_turns` reached — both map onto the single `BUDGET_EXHAUSTED` token/`budget_exhausted` status value defined below; there is no separate enum value per cap, only a distinguishing note) so the two caps remain individually diagnosable without adding a fifth status value to the charter's Domain Model enum. This closes the write-only gap: `bugs_attempted[]` is appended to once per completed attempt (existing behavior) and is now also read back, every turn, specifically to enforce `--max-bugs`; `turns_completed` is incremented once at the end of every turn (attempt or not) and read back to enforce `--max-turns`. If neither budget is exhausted, the turn proceeds to bug selection below.
- Each turn (once the budget check above has passed): `adev issues next --type bug --max-priority P3 --json` (per the sibling `bug-selection-and-eligibility` spec) → `adev issues claim <id> --owner bugfix-loop --branch <current branch>` (`--owner bugfix-loop` is a fixed literal identifying the automated loop, distinct from any human owner string) → **sets `ADEV_ISSUE_OWNER=bugfix-loop` in the environment for the `/adev:debug` invocation specifically** → `/adev:debug --issue <id> --apply --auto` (per the sibling `debug-completion-and-auto` spec) → reads the resulting `ADEV-DEBUG:` token → **writes/updates the issue's `AttemptRecord` per the sibling `per-issue-attempt-cap` spec's BEH-1/2/3, mapping the token (`FIXED`/`PARKED`/`UNREPRODUCIBLE`) onto that spec's write contract; the check-ID data for `PARKED` is read from `IssueManager.get(id).notes`'s `FAILING-CHECKS:` block, per `debug-completion-and-auto`'s BEH-8** → `adev issues release <id> --owner bugfix-loop`. Regardless of outcome, the turn then appends to `bugs_attempted[]` (on a completed attempt) and increments `turns_completed` by 1 before self-re-invoking (see Invocation Modes' automatic-re-invocation clause). The skill never marks a bug fixed itself; `FIXED` outcomes are entirely `/adev:debug`'s own Phase 6 confidence gate (charter invariant — restated here as the skill's binding contract, not re-derived). The loop's own `adev issues claim` and `/adev:debug`'s internal Phase 1.6 claim (fired whenever `--issue <id>` is passed) target the same issue and owner **only because `ADEV_ISSUE_OWNER` is explicitly propagated** — `skills/debug/SKILL.md`'s Phase 1.6 (`skills/debug/SKILL.md:163,168,180`) now resolves the owner from `ADEV_ISSUE_OWNER` when set, falling back to `--owner "${USER}/local"` only when unset, per the sibling `debug-completion-and-auto` spec's BEH-9 fix — already shipped, built, and validated, not pending work. This shipped behavior is what makes the loop's claim and `/adev:debug`'s re-claim target the same owner string. Had BEH-9 not shipped, this claim/re-claim pair would refuse with `ISSUE_ALREADY_CLAIMED` on every turn — this was a real (now-satisfied) dependency, not incidental idempotency.
- When `--github-sync` is set, additionally invokes the tracker-provider-bridge's inbound pull before selection and outbound writeback after each attempt.
- Includes a Load Skill Extensions block invoking `adev skill-ext load --skill bugfix-loop`, per the constitution's requirement that every new skill carry one.
- Emits a terminal `ADEV-BUGFIXLOOP: <STATE>` completion token as the final chat line, following the grammar pinned in `completion-tokens.spec.md` — states: `COMPLETE` (board drained, no eligible bugs remain), `BUDGET_EXHAUSTED` (`--max-bugs`/`--max-turns` hit while eligible bugs remain), `BLOCKED` (a structural failure, e.g. issue board unreachable, halted the run before any bug was attempted). **Completion-token-to-persisted-status mapping:** immediately before emitting the token, the skill writes `BugfixLoopRun.status` in the run-state file using the charter's Domain Model enum (`running`/`complete`/`budget_exhausted`/`blocked`, the fourth value added specifically for this case) — `COMPLETE` → `status: complete`, `BUDGET_EXHAUSTED` → `status: budget_exhausted`, `BLOCKED` → `status: blocked`. `status` starts `running` at run creation and transitions exactly once, to whichever of these three values matches the terminal token, on the run's terminal turn; there is no persisted value that lacks a corresponding token or vice versa. **`degraded_sync_note` consumer behavior:** immediately before printing this token, on whichever turn ends up terminal, the skill re-reads `BugfixLoopRun.degraded_sync_note` from the run-state file it already has open for the write that accompanies this token. If it is non-null, the skill prints one additional chat line — `GitHub sync degraded during this run: <degraded_sync_note>` — directly above the token line (the token itself is still unconditionally the literal last line of output, so this does not violate the "always the literal last line" / no-footer-after-token rule below). If it is null, no such line is printed. This read-and-surface step is this field's only consumer anywhere in the charter — the sibling `tracker-provider-bridge` spec is the sole writer (Error Propagation, 5th consecutive degraded sync turn) and this bullet is the sole reader, closing the write-only gap between them without requiring a new `/adev:status` surface. This is a fourth terminal skill added to that cross-cutting convention, alongside `build`/`validate`/`debug` — coordinate a Task Map addition there rather than fork the grammar. **Persona-exempt, matching `build`/`validate`/`debug`:** `skills/using-adev/SKILL.md`'s Persona Output Override carve-out is extended to name `ADEV-BUGFIXLOOP` explicitly (that bullet is enumerated per-skill, same gap the sibling `debug-completion-and-auto` spec's BEH-6 closed for `ADEV-DEBUG` — this spec closes it for its own new token rather than assuming inheritance). **Excluded from spine-skill chaining:** per `single-front-door.spec.md`'s Failure Modes ("Spine-skill footer would follow a completion token | Excluded by contract"), `/adev:bugfix-loop` — like `build`/`validate` — never appends a "Next Step in the Lifecycle" footer after this token; the token is always the literal last line.

## Failure Modes

| Condition | Skill Behavior | User Recovery |
|---|---|---|
| Issue board unreachable or `tasks.backend` misconfigured | Loop halts immediately on the first turn; does not silently retry; run-state file is written with `status: blocked` (per the charter's Domain Model enum) before the `ADEV-BUGFIXLOOP: BLOCKED` token is emitted | Fix `manifest.yaml`'s `tasks.backend`, re-run |
| A selected bug's claim fails (lease race — already claimed by another session) | Skip to the next eligible bug within the same turn, **bounded to at most 3 claim-failure retries per turn**. `adev issues claim` failures release no lease, so the failed bug is not re-eligible until its own lease naturally expires — `adev issues next` will not re-surface it within this turn. If the 3-retry bound is exhausted without a successful claim, the turn ends without an attempt and **counts toward `--max-turns`** (self-re-invokes normally) rather than looping further — this bound exists specifically so contention can never bypass `--max-turns` by spinning inside a single turn | None needed — self-heals across turns as leases expire |
| `/adev:debug --auto` errors out entirely (crashes, rather than reaching a clean `PARKED`/`UNREPRODUCIBLE` token) | Treated as `PARKED` with an explanatory note; the claim is released; the loop continues to the next bug rather than halting the run | Review the crashed bug's issue notes; investigate manually |
| `--github-sync` set but the tracker-provider-bridge capability is not yet implemented | Fails fast on the first turn with a clear "GitHub sync not available" error, rather than silently ignoring the flag | Omit `--github-sync`, or wait for that capability to ship |
| `--max-turns` exhausted with eligible bugs still remaining | Loop stops cleanly, emits `BUDGET_EXHAUSTED`; remaining bugs are left untouched (not parked — simply not attempted this run) | Re-run `/adev:bugfix-loop` to continue, or raise `--max-turns` |
| `--max-bugs` reached (`bugs_attempted.length >= max_bugs`) with eligible bugs still remaining | Detected by the per-turn budget check, before `adev issues next` is called on that turn — the turn attempts no bug, stops cleanly, emits `BUDGET_EXHAUSTED`; remaining bugs are left untouched (not parked — simply not attempted this run) | Re-run `/adev:bugfix-loop` to continue, or raise `--max-bugs` |
| A `PARKED` bug (`CONTINUE` verdict, under its attempt cap) is re-selected on a later turn or run | Expected, not a failure — per the sibling `per-issue-attempt-cap` spec, only `NO_PROGRESS`/`REGRESSED`/`BUDGET_EXHAUSTED` verdicts exclude an issue from `adev issues next`; a `CONTINUE` verdict means another attempt is exactly what should happen next. "Board drained" (`COMPLETE`) is reachable once every remaining bug has hit one of those three excluding verdicts or `FIXED` | None needed — this is the intended retry-until-cap design |

## Acceptance Criteria

- [ ] `/adev:bugfix-loop` processes exactly one bug per turn and self-re-invokes until the board is drained or a budget is hit
- [ ] Self-re-invocation between non-terminal turns is automatic (the skill's own last action each such turn, no human action required) — verified by a test that runs 2+ turns end-to-end with no simulated human input between them and confirms the second turn executes
- [ ] The per-turn budget check enforces `--max-bugs`: a test seeds a run-state file with `bugs_attempted.length == max_bugs` and asserts the next turn terminates with `ADEV-BUGFIXLOOP: BUDGET_EXHAUSTED` (and `status: budget_exhausted`) without calling `adev issues next` or attempting another bug
- [ ] The per-turn budget check enforces `--max-turns` via `turns_completed` (not `bugs_attempted.length`, which does not increment on claim-failure-exhausted turns) — a test seeds `turns_completed == max_turns` and asserts the same no-attempt `BUDGET_EXHAUSTED` termination
- [ ] The skill never marks a bug fixed except via `/adev:debug`'s own `ADEV-DEBUG: FIXED` token
- [ ] A Load Skill Extensions block is present and invoked
- [ ] `ADEV-BUGFIXLOOP: COMPLETE | BUDGET_EXHAUSTED | BLOCKED` is emitted correctly as the final line, matching the pinned grammar exactly (verified against the regex, not just visually)
- [ ] `BugfixLoopRun.status` in the run-state file is set to the value matching the emitted token (`complete`/`budget_exhausted`/`blocked` respectively, per the charter's Domain Model enum) before that token is printed — verified by a test that forces each of the three terminal paths (including the board-unreachable `BLOCKED` path) and asserts the persisted `status` field, not just the printed token
- [ ] On turn start, the skill reads its own prior `BugfixLoopRun.status` and refuses to proceed — no `adev issues next` call, no `bugs_attempted[]`/`turns_completed` mutation, no completion token re-printed — exiting non-zero instead when `status` is not `running` — verified by a test that seeds a terminal `status` value (e.g. `complete`) in run state before invoking a turn and asserts the turn exits with the refusal rather than attempting a bug
- [ ] When `degraded_sync_note` is non-null at run end, a `GitHub sync degraded during this run: <degraded_sync_note>` line is printed immediately before the `ADEV-BUGFIXLOOP:` token, and no such line is printed when it is null; the token remains the literal last line in both cases — verified by a test that seeds a non-null `degraded_sync_note` in run state and asserts the warning line is actually emitted (not merely that the sibling spec describes the write)
- [ ] `--github-sync` fails fast with a clear error when the bridge capability isn't yet available, rather than silently no-op-ing
- [ ] Claim/release discipline holds even when `/adev:debug` crashes mid-attempt — no orphaned claims
- [ ] `BugfixLoopRun` state persists across self-re-invoked turns and survives a process restart mid-run
- [ ] `bugfix-loop-runs-<run_id>.json` is confirmed git-ignored (`git check-ignore` passes) before implementation is considered complete
- [ ] Claim-failure retries within a single turn are bounded to 3 and the turn still counts toward `--max-turns` on exhaustion — verified with a test that forces repeated claim contention
- [ ] `AttemptRecord` is written after every completed attempt, verified by a test asserting the write actually happens (not just that the sibling spec describes it)
- [ ] `adev issues claim`/`release` calls use `--owner bugfix-loop` on both ends; `/adev:debug`'s internal Phase 1.6 re-claim succeeds (not `ISSUE_ALREADY_CLAIMED`) because `ADEV_ISSUE_OWNER=bugfix-loop` is set for that invocation
- [ ] `ADEV-BUGFIXLOOP` is added to `skills/using-adev/SKILL.md`'s Persona Output Override carve-out and verified persona-exempt across Product/Architect personas
- [ ] `bugfix-loop-runs-<run_id>.json`'s format/ownership is registered in ADR-0015's Decision-section table
- [ ] `/adev:work` and `using-adev`'s gateway listing include an entry for `/adev:bugfix-loop`
- [ ] All quality gates pass (`npm test`)
