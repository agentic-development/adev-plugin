# ADR 0007: Conventional Commit Message Enforcement

## Status

Accepted

## Date

2026-05-10

## Context

The project adopted release-please for automated releases (ADR 0008). Release-please relies on conventional commit prefixes (`feat:`, `fix:`, etc.) to determine version bumps and generate changelogs. Without enforcement, non-conforming commit messages are silently ignored — features go unrecorded in changelogs, and version bumps may be incorrect.

The project already has a `commit-msg` git hook for Spec trailer enforcement and a CI step for provenance trailer validation. Both are natural integration points.

## Decision

Add conventional commit subject validation at two enforcement layers:

1. **Local (commit-msg hook):** Validates the commit subject line against allowed types before any other checks. Blocks non-conforming commits with an actionable error message. Runs before the Spec trailer and lifecycle checks.

2. **CI (provenance check step):** Validates commit subjects in PRs against the same allowed types list. Catches commits made with `--no-verify` or from environments without hooks installed.

Allowed types are configured in `manifest.yaml` under `provenance.conventional_commit_types`, making them project-configurable rather than hardcoded. The initial set includes 13 types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`, `deps`, `research`.

Merge commits, fixup commits, squash commits, and amend commits are exempt from validation (auto-generated by git).

## Consequences

- All commits must use the `<type>[(<scope>)][!]: <description>` format
- The allowed types list is the single source of truth, read by both the hook and CI
- Adding a new type requires only editing `manifest.yaml` — no code changes
- Non-conforming historical commits are unaffected (validation is forward-looking only)
- Agents (Claude Code) must use conventional prefixes, which aligns with existing practice
